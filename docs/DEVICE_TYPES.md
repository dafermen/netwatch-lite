# Device Type Catalog

## Operator Workflow

Open **Device Types** (`/device-types`) from the sidebar, or **Manage types**
from the device editor. The active support group/region is shown above the
catalog. Add a custom type, rename its display name, or delete it when unused.
Search by name/ID and filter protected, custom, used or unused types. Device
counts include monitoring-disabled records.

In Configuration, select the type in the Device Type dropdown. It is separate
from Category (display grouping) and Checks (ping/TCP/HTTP monitoring). For a
web application, a custom type such as Web application is only classification;
configure an HTTP/HTTPS check to monitor its URL.

Dashboard also offers Device Type immediately before Category. It reads this
profile's catalog and filters both pending and checked inventory; scoped runs
enforce the selection before executing checks. See [dashboard filters](DASHBOARD_FILTERS.md)
for shared filter intersections, filtered automatic runs and no-match behavior. New
results snapshot their classification and scoped history records the selected
type ID; missing legacy classifications remain unknown, without rewriting history.

The five original system types remain protected:

| Stable ID | Name | Special behavior |
| --- | --- | --- |
| `unspecified` | Not specified | Default for old/unclassified records. |
| `workstation` | Workstation | Enables manually recorded printer/scanner inventory and the Workstations view. |
| `server` | Server | Classification only. |
| `network` | Network device | Classification only. |
| `other` | Other | Classification only. |

Their IDs and names cannot be removed or renamed, including through API calls
and JSON import. Custom types cannot acquire workstation behavior by name or
extra flags. Only `deviceType: "workstation"` enables it. Changing a recorded
workstation to another type still requires confirmation in the device editor;
the backend rejects peripheral assignments on other types.

Custom IDs are stable and generated by the UI; renaming changes only the
display name, including for types in use. Deletion is blocked while any device
references the type. Reassign or remove those devices first. The catalog does
not delete or reclassify devices automatically.

## Storage And Compatibility

The catalog is the `deviceTypes` array in each support-group configuration,
not a separate database or runtime file. It travels with devices, peripheral
models and assignments on export/import and support-group copies. A new
independent profile starts with the five defaults; it does not share custom
types with other groups.

```json
{
  "deviceTypes": [
    { "id": "unspecified", "name": "Not specified" },
    { "id": "workstation", "name": "Workstation" },
    { "id": "server", "name": "Server" },
    { "id": "network", "name": "Network device" },
    { "id": "other", "name": "Other" },
    { "id": "web-app", "name": "Web application" }
  ],
  "devices": [
    { "name": "Example portal", "ip": "127.0.0.1", "deviceType": "web-app",
      "checks": [{ "type": "http", "url": "http://127.0.0.1:5000/" }] }
  ]
}
```

This is an illustrative local example, not an operational target to import
unchanged. Existing files without `deviceTypes` load the five defaults in
memory. Their device keys stay valid; absent/blank device types remain
unspecified, and categories are never used to infer types. Reads of existing
files do not perform a migration write. A later save/export includes the new
field. Existing history and monitoring checks are unchanged.

Explicit null/empty catalogs and missing protected entries are invalid, not
silently repaired. Whole-configuration POST/import remains full replacement:
new clients must include `deviceTypes`. A legacy payload without the field
loads defaults, removes unused custom definitions on replacement, and is
rejected if it references custom keys not declared in the catalog. An older
binary does not understand custom types; back up compatible configuration
before downgrading and do not save new profiles through it.

## Validation

- At most 200 entries, including the five protected defaults.
- IDs: 1-80 ASCII letters/digits/hyphens/underscores, starting with a letter;
  trimmed and normalized to lowercase. IDs must be unique ignoring case.
- Names: required, at most 100 characters, no control characters; trimmed and
  unique ignoring case. Protected names must retain their canonical spelling.
- Every device's type must resolve, including disabled devices. Null entries
  and undeclared references fail before atomic persistence.
- Labels are rendered as text, not HTML. IDs cannot inject selectors/paths.

## Catalog-Only API

GET `/api/device-types` returns `profileId`, `profileName`, `region`, opaque
`version`, `protectedIds`, `deviceTypes` and `usage` (device count by type).
It captures profile identity and data from the same profile path. No file path
is returned by this endpoint.

POST `/api/device-types` takes:

```json
{
  "profileId": "<from GET>",
  "version": "<from GET>",
  "deviceTypes": [
    { "id": "unspecified", "name": "Not specified" },
    { "id": "workstation", "name": "Workstation" },
    { "id": "server", "name": "Server" },
    { "id": "network", "name": "Network device" },
    { "id": "other", "name": "Other" },
    { "id": "web-app", "name": "Web application" }
  ]
}
```

Replace the profile/version placeholders with values from GET and submit its
actual full array with the intended changes. Success returns a fresh snapshot.
An invalid catalog or in-use deletion returns HTTP 400 with `error`. A changed
active profile/catalog returns HTTP 409 with `error`; reload before retrying.
Treat the version as opaque. It identifies the normalized catalog, independent
of ordering, not the entire inventory.

The repository holds its configuration write lock, reads current inventory
from the captured profile file and replaces only `deviceTypes`. It therefore
preserves another editor's row/settings/peripheral changes. It validates fresh
references even if usage changed since GET. Simultaneous catalog edits using
one revision yield one success and one conflict. A profile switch detected at
capture rejects an old editor; a switch after capture cannot redirect its write
to the new profile. Profile registry and profile files are not one transaction.
Only one application writer process is supported per data directory.

These protections apply to the catalog-only endpoint. Whole-document config
saves/imports retain their existing replacement semantics and are not given
global multi-editor version control by this feature. The app still has no
authentication/roles: keep it within trusted host/network controls.

Failed loads clear old catalog rows and disable editing until retry succeeds.
Conflicts preserve the open name draft and offer an explicit Reload catalog;
that action discards the stale draft. Navigating from the device editor to
Manage types asks before discarding its unsaved device changes.
